# Pre-1 review: coverage and remaining decisions

Candidate 0.19 is an incremental result, not a readiness declaration or definition of 1.0. The user must review acceptable supported scope before any version transition. In-app composition is primary; portability is a possible secondary benefit with uncertain demand. Exact Chorus parity and complete replication of every historical example are not prerequisites.

## Observed core evidence

| Authoring need | Verified candidate evidence | Boundaries |
|---|---|---|
| New activities through reusable operations | 23 package examples; held-out check-in/story, pools/pairs, scoring/private reflection, recurrence/pairs, random linked response/pairs, image/story; independent engines and durable hosts | Ordered runbooks; bounded loops/windows; no arbitrary code or general concurrent branches |
| Adjustable behavior in the host app | Saved typed prompt/time settings, explicit close/visibility/audience policies, exact routing/scoring/distribution policies, structural inspector | Settings bind at instance creation; no live edits, rich authoring UI or plugin marketplace |
| User contributions and privacy | Text/choice/list/index/integer fields and image references; private/group projections; explicit reveal; source-linked text response | Group collection, source pools and linked responses remain text-only; no audio/video |
| Timing and repeated practice | Scheduled waits/deadline collection, fixed bounded recurrence, independent responses, completion/missed status and long worker jumps | No dynamic recurrence, late-source threshold or general overlapping activity streams |
| Useful distribution algorithms | Deterministic next non-self contributor and seeded non-self sampling; eligibility, one-source/reuse/unmatched rules; durable saved outcomes | No two-option choice, exposure fairness, crypto randomness or image-source distribution |
| Host correctness | Authenticated ordered events, durable accepted ledger, exact retries, races, immutable package identity, capability rejection before state creation, cross-language recovery/transfer | Local SQLite HTTP reference profile; package exchange does not migrate running instances/blobs or prove production integrations |
| Older examples retained honestly | Six exact legacy migrations with comparisons; fourteen remain explicitly incomplete | Simplified witnesses do not silently count as full migrations |

## Review-essential remaining work

The readiness review needs a fresh bounded coverage challenge against the current composed candidate, with externally selected/held-out activities and explicit supported/unsupported outcomes. The historical eight-pattern 0.12 challenge is useful evidence of earlier deficits but is not a current readiness test. Reuse demonstrations already pass; the remaining task is to assess sufficient activity breadth, including combinations not hand-selected to fit existing operations.

Review authoring clarity and the embedding contract as a whole: which settings/algorithms are exposed, how unsupported choices are presented, which trusted actor/clock/media guarantees a host must provide, and which projections should prompt participants. Notification delivery/permissions and what starts a time-sensitive deadline remain open integration questions in the existing research record; no new universal delivery requirement is invented here.

The user must choose whether ongoing progress alongside a final deadline and typed image source distribution are essential to the intended initial experience. They are the most plausible capability gaps for broader creative activities: current image forms do not by themselves enable a simplified image-cover Chorus. They should be investigated through a concrete held-out witness rather than implemented solely to complete a legacy checklist. A bounded reference-valued source/linked-response slice may be useful; no media infrastructure or full Chorus replication is implied. General concurrency is not justified by existing evidence.

Before any 1.0 transition, prepare the proposed supported profile, explicit exclusions, remaining failures and full test evidence for user review. Determine version/compatibility/release choices separately. There is no automatic transition, fixed candidate count or claim that all group activities are expressible.

## Optional or scope-dependent extensions

Two-cover offers, participant choice, exposure balancing, detailed legacy facilitator/feedback rules, voting variants and product-specific phase branches are optional parity refinements. Replacement/moderation, organizer participation, live schedule edits, broader image encodings in the reference upload profile, audio/video and dynamic recurrence are scope-dependent capabilities; they remain unsupported and must be disclosed wherever an activity needs them. Full migration of all fourteen older examples is not an automatic readiness gate.

Uploads/transcoding/scanning, draft autosave, notifications, realtime/cache, UI cards, chat, public boards, and transactionally publishing application records belong to host integration. Production safety/scalability certification, deployment and universal cross-platform portability have not been established by local trials and are not claimed.

**Next recommended work:** run a current held-out coverage/readiness challenge and review the supported profile. Use its failures to decide whether one bounded core extension is necessary; avoid automatically chasing every historical detail. Stop before 1.0 for the user's decision.
