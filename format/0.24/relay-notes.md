# First valid contribution and rolling invitations

`first_valid@1` is a top-level collection instruction. It accepts one finished typed contribution from one of two invitees; the first valid authoritative acceptance is canonical. Invalid or unready submissions leave both opportunities open. Validation, immutable entry, qualified canonical output, queue transition, accepted event ID and phase closure commit in one serial host transaction. A loser rejects even at the same timestamp. Upload start, client send time and first claim do not establish precedence.

## Author configuration

Required fields: `id,op,prompt,kinds,policy,windowMs,retryAfterMs,input,queueInput`. `policy` is `policy:rolling_pair@1`; `kinds` is a distinct nonempty subset of text/image/audio. Durations are integer milliseconds from 1 through 604800000 (seven days). The creative relay examples use 86400000 for both window and failed-pass retry delay. These are package configuration, independent of accepted kind. `input` is null or `{binding:<declared contribution input>}`; `queueInput` is null or `{binding:<declared queue input>}`. No anonymous canonical material or implicit queue guessing.

Optional top-level `queueInputs` declares up to eight `{type:"invitation_queue"}` bindings. Each is used exactly once, by a first-valid step; no orphan declaration or alias reuse. `input` uses the retained `inputs` contribution declaration and qualified all-viewer authority. New capabilities are `first_valid@1`, `policy:rolling_pair@1`, `invitation_queue@1`; retained `seeded_assignment@1`, host controls and declared media capabilities are also required. This version is top-level only and does not widen any historical consumer source family.

## Queue transitions

An initial invocation shuffles its participants once using saved xorshift32 draws and descending Fisher–Yates swaps. A continuation uses the supplied saved order, retaining current members in that order and appending new members in current enrollment order. No reshuffle on exhaustion or restart. The participant roster controls invitation eligibility; bound identities can continue reading history after withdrawal. A participating organizer receives no extra submission privilege.

Select the first two eligible people, excluding the canonical author on every opening and replacement. In an unsuccessful pass, prefer people not yet attempted, retaining any current partner. An odd tail pairs its unattempted person with the earliest attempted eligible person. An invitation offer carries `generation,actors,invitations,opensAt,closesAt`; each invitation is `{actor,key,opensAt}`. The numeric ticket counter is private runtime state. A replacement gets a fresh ticket; a retained partner keeps their own ticket, original opening and shared closing boundary. A batch generation identifies a changed offer for delivery, not submission authority.

On valid acceptance, promote the other invitee to the front; retain the relative order of every other person; put the winner at the back. For canonical A with order `[A,B,C,D]`, B+C race; B wins; output order is `[C,A,D,B]`. C+A are invited next because B is now excluded. A new host-launched invocation starts a fresh shared window for both. Carry-over intentionally resets the losing person's invitation clock, so a nonparticipant can remain invited indefinitely while partners submit promptly. Opportunity is preserved, not a guaranteed win.

At exclusive closing (`at >= closesAt`), both current invitees move to the back in offer order. Mark both attempted, count one failed transition, and open the next eligible pair against unchanged canonical material. A late worker opens the fresh window at its observed time; it does not expire invitations which were never available to participants. Decline moves only that person back, marks them attempted, counts one failed transition, and fills their slot within the existing shared deadline. A retained partner's ticket stays valid. There is no three-person race.

Trusted `roster` replaces active membership. Retain survivors in queue order, append newcomers and preserve exclusion. If an invitee leaves, mark their failed opportunity and count one replacement transition; retained tickets remain valid while missing slots refill within the same deadline. Previously failed identities stay attempted after withdrawal/readdition. Before expanding bound viewers, reauthorize every retained contribution binding and every retained immutable queue snapshot for the entire expanded audience. This applies to roster changes and later window configuration, even after the first-valid step closes. Reject before changing roster, hostActors, projections, grants or tokens. The demo hosts deny wholly unbound source viewers; people prebound in each origin may join/rejoin. An initial empty run has no canonical material requiring a read grant, but its saved queue metadata still requires separate audience authority. Queue copying or token creation alone cannot grant image bytes.

## Completion, bounds and clock

`output` is `{status,reason,selected,canonical,queue}`. On `selected`, selected/canonical are the actual qualified contribution `{ref:{instance,source,itemId},actor,value,round:null}`. Other statuses have selected:null and retain the predecessor canonical or null. Closed records alone publish queue output. A queue is `{ref:{instance,source},order,canonical:<qualified ref or null>,notBefore}`.

- `paused / insufficient_members`: fewer than two eligible people. A continuing group normally needs three available people after excluding its latest author.
- `exhausted / pass_complete`: every currently eligible identity had a declined/expired opportunity during this invocation.
- `exhausted / failure_budget`: 100 failed expiry, decline or invitee-replacement transitions occurred, including under membership churn. This internal bound is not an author setting; a two-person expiry counts once. At the 99-transition state, the next two-person expiry completes transition 100 and ends the invocation. There are at most 200 expired/declined/replaced individual opportunities, 100 current members and 256 lifetime bound identities. Failed identities and accepted IDs survive restart.
- `clock_exhausted / clock_limit`: a full fresh window and retry delay cannot fit the safe integer clock range. The output has notBefore:null and is non-resumable. No deadline or cooldown is shortened by clamping.

Paused/exhausted completion exports `notBefore = observed closing time + retryAfterMs`. The host may launch a successor at or after that boundary; the successor starts a fresh failed pass, preserving queue and canonical material. Selected output permits immediate continuation. A null canonical requires `input:null`; a non-null canonical requires a qualified contribution binding with exactly the queue's canonical ref. Near clock exhaustion, construction rejects an unsafe conservative timing budget; later observations may terminate non-resumably. A retry must not reopen a consumed source or change its order.

## Events and durable host protocol

A submit payload is `{invitation:<own ticket key>,predecessor:<current qualified ref or null>,itemId,value}`. Decline uses the first two fields. Retained accepted-event IDs replay across deadlines and restart; changed payload/actor/step conflicts reject. Wrong ticket, prior invocation path, stale predecessor, noninvitee, withdrawn actor, wrong kind, malformed value, foreign owner or unready media rejects. Temporal settlement can still expire an offer while processing an invalid request. Values keep immutable owner/source identity and the retained media authorization rules.

`Engine` adds `queue_bindings,authorize_queue` in Python and `queueBindings,authorizeQueue` in JavaScript. The trusted callback attests the whole immutable snapshot and all destination viewers. Restored state trusts the durable host's previously attested input; supplied restored bindings must match. Restore must also reconnect the trusted callback for any later audience expansion; without it, expansion with retained queues fails closed. Every retained queue is checked, not just the current step's binding. Engine fixtures use `queueBindings` plus `trustedQueues` assertions for test authority; these are not client credentials.

The validation hosts accept admin `hostQueues:{binding:{instance:<local instance ID>,source:<step ID>}}` at creation. They resolve only a closed actual `first_valid@1` record, preserve its globally qualified source ref and check every destination viewer's origin binding. Canonical material uses existing `hostBindings` direct contribution pointers with immutable true origin and provenance. No voting or renamed/copied item is needed. A failed pass may refer to a canonical contribution from an earlier instance; the host must bind that true contribution origin, not invent an item in the failed instance.

The source consumption key is `(qualified source instance UUID, source step)`, independent of binding alias or destination ID. Validate package/capabilities, roster, clocks, exact queue snapshot, canonical match, authority, and duplicate refs before claiming. Source claim, successor state/identity, input grants, actor tokens and creation receipt commit together. Failed setup leaves no target or claim. Competing successor IDs yield one creation and one `queue_consumed` result. Multiple aliases of one ref reject before consumption.

For relay instances, an exact admin creation request retry returns `existing` with the original local ID, immutable identity and digest, even after the original offers expire; changed requests return `instance_conflict`. The retry does not create or reshuffle. Original credentials are not stored in plaintext; if the first response was lost, the trusted host may rebind credentials for already bound actors. The host alone supplies clock, persistence, media infrastructure, notifications and successor launch. No notification delivery or calendar workflow is implemented by this language instruction.
