# Generic typed pooling and compatible consumers

Candidate 0.24 adds a consistent typed pool with author-selected kinds and per-person limits. These are new operation versions; retained text and typed contracts remain exact. This note is normative for the new instructions, alongside retained [operations](operations.md), [input authority](input-notes.md), [voting](voting-notes.md) and [typed values/controls](artifact-notes.md).

## Pool independent items

`pool@2` requires exactly `id,op,prompt,kinds,perActor,visibility`, with optional `round,input`. Kinds is a nonempty distinct subset of text/image/audio. `perActor` is an integer 1–8, one shared maximum across all accepted kinds. It is not a required minimum, a separate allowance per kind or a replacement setting. The optional round defaults null; explicit null is equivalent. A non-null round is a valid name unique among typed and routed rounds within this package. Optional input defaults null; it can be `{binding:<declared contribution name>}` or `{result:<preceding select@2/select@3>}`. Anonymous values, text labels and executable expressions are not input references.

The exact submission payload is `{itemId,value}` with the retained typed value/authority rules. Each immutable item ID is unique across this pool invocation. Equal text or the same ready owned media under distinct IDs are independent contributions. Quota use counts every accepted entry from that actor, including before withdrawal/readdition. Changed accepted-event reuse, duplicate IDs, overflow, wrong kinds, foreign/unready media, stale keys and late actions reject atomically. A rejected attempt consumes no quota or accepted-event identity. Exact accepted retries replay without reauthorization, duplication or changes to later decisions.

Pool actors/dates, configure/close, whole-input authorization and media ownership follow retained host controls. Opening is inclusive; closing exclusive. Filling all limits does not close the window. Final source eligibility uses the frozen effective actor list at source closure; withdrawn entries remain in private/group history and ledger but are excluded by later consumers. No missing quota slot becomes an item. Private entries go only to their author; group entries are attributed immediately. Public count is total accepted history, not an anonymity guarantee. Views include round/input/blocked status, quota, ownCount/remaining and visible qualified contributions.

## Source types and early validation

The compatible typed source family for new iteration, voting and assignment is `artifact_pool@1`, `artifact_pool@2`, `artifact_pool@3`, `pool@2`. Each provides accepted typed material and final effective actor ordering. New consumers produce the established qualified `{ref:{instance,source,itemId},actor,value,round}` snapshot; round may be null. The stable host UUID identifies actual material, with no relabeling or copied rendered value.

Semantic validation checks preceding sources, scope, kinds/capabilities, input/output types and operation versions before setup. New consumers handle all three language kinds; author settings need not repeat the producer's kinds. Old text `pool@1` remains an untyped-text contract with its own item/scoring/source consumers. Old consumers cannot silently accept a new generic pool, even when it happens to accept only text. There is no arbitrary form/response/result adapter, video or unrestricted type registry. Schema alone cannot enforce cross-step typing; both semantic validators must run. Capability negotiation rejects unsupported instructions before state/grants exist.

## Iterate and explicitly share

`for_items@2` has exactly `id,op,source,policy,steps`; it is top-level and uses `policy:pool_order@1`. On entry it snapshots final-eligible accepted items in commit order, plus the final source-effective actor list. Body execution keys are `id:iteration`; original item IDs are not execution keys. Empty pools and missing slots create no iteration. Snapshot values/authors/media/readers remain internal; public item context contains only the qualified ref. There is no public loop wrapper record. At most 800 eligible items can expand (100 effective actors × limit eight).

Bodies retain existing item-body restrictions: ordinary collect/reveal/tally/pause instructions plus the three new typed item instructions; no repetition, new pool/vote/assignment or older top-level-only operation is smuggled into a body. Body outputs remain local and cannot be referenced later at top level. Ordinary instructions still execute after a skipped reveal; no hidden conditional/dependency workflow is inferred.

`assign_item@2` fields are `id,op,policy,prompt,afterMs`, with `policy:claim_reader@1`. Readers are frozen final source-effective actors, including noncontributors, minus the current author. A participating organizer is eligible only through that same list. The first accepted ordered claim sets one reader. With no possible reader, skip immediately; otherwise a nullable retained relative timeout may end with none. A public reader and canClaim flag reveal no private value. Only that reader receives `assignment:<qualified contribution>`, including actual author/round/value, before explicit publication. Self, outsiders, later competing claims and stale keys reject; accepted claim retries replay.

`acknowledge@2` fields are `id,op,source,prompt,afterMs`, referencing an earlier typed assignment in this body. Only its reader can advance. Without a reader, skip false; timeout records false; acceptance records true. It proves an app acknowledgment, not speech or listening. Reader-only access to the saved material persists in history across later timeouts and restart.

`reveal_item@2` fields are `id,op,source`, referencing the earlier typed acknowledgment. True publishes that actual attributed qualified contribution to all bound viewers in a reveal record; false publishes null. This explicit output grants projection-based reads without broadening an old pool's visibility contract. These new operations are attributed sharing; old anonymous text versions remain unchanged. Merely knowing an item/media ref confers no access or submission ownership.

## Vote, select and continue

`vote@3`, `tally@4`, `select@3`, `present@3`, `reveal_ballots@3` retain the corresponding 0.22 qualified-chain fields/output/current-vote/privacy/retry/closing rules, with the compatible typed source family above. Every accepted eligible item is a separate candidate, including several items by one actor and equal values under different IDs. New candidate payloads carry the full actual qualified ref. Candidate material and attribution publish on voting entry; individual private ballots remain private after counts/outcome presentation unless explicitly revealed.

Structured outcomes and bases remain exact: most_votes, random_tie, random_no_votes or retained_input; unresolved ties/no_votes/no_candidates have no fabricated selection. All noVotes settings preserve no_candidates for an empty pool. Retention is valid only for an actual qualified starting input in artifact_pool@3 or pool@2; anonymous old literals cannot become retained attributed material. New pool inputs may consume select@2 or select@3; old pool/result versions keep their restrictions. Random tie/no-vote policies retain equal-chance membership and durable selection without prescribing cross-host streams. General presentation remains separate from calculation.

## Assign one source and independently respond

`assign_artifacts@2` has retained fields `id,op,source,policy,recipients,cardinality,reuse,unmatched`, with compatible typed source and `cardinality:one,reuse:allowed,unmatched:skip`. Recipients are unique frozen effective actors in their order, or the contributing subset; multiple items never duplicate recipients. All policies exclude the recipient's own items.

New `policy:next_nonself_item@1` chooses the next eligible author cyclically in source-effective order, then that author's earliest eligible accepted item. The old single-entry deterministic policy is unchanged. Retained `policy:seeded_nonself_source@1` samples eligible items in commit order using its exact saved sampler and recipients in effective order. Zero/one candidates consume no draw. An author submitting more items may receive more exposure under item sampling; no balancing/fairness promise is added. Empty/self-only cases are unmatched; no self fallback or wait-for-more branch is inferred.

Assignment saves `{actor,candidate:<qualified contribution>}`; only the recipient sees its actual attributed assignment. `artifact_response@2` retains fields `id,op,source,prompt,kinds`, references the saved new assignment, and accepts one immutable independent response per effective matched actor. Its exact payload is `{candidate:<assigned qualified ref>,value}`. Wrong origin/source/item, extra replies and foreign/unready/wrong-kind values reject. Response history is `{actor,source:<qualified contribution>,value}`. Quota changes in the source pool do not change response cardinality. Effective controls do not reroll assignments.

`reveal_artifact_responses@2` fields are `id,op,source`; it explicitly publishes accepted linked source/response pairs with attribution. Unused source material remains private. Before reveal, responses go only to their author; assignment access remains only with the recipient. New instructions are top-level; host media grants follow actual projections, not reference possession or new ownership.

## Execution/host boundary

UUID identity, declared input/via authority, every viewer including future/later actors, origin media retention and projection-based read grants retain 0.22 guarantees. Hosts supply clocks/accounts/actors/dates, process/store/render media, authenticate requests, serialize transactions and persist accepted effects/ledger/choices before returning. No provider protocol, successor stream, calendar, role engine or product-specific dispatch is introduced.

Conservative safe-clock budgeting includes up to 100 source actors and each pool's maximum quota, even when host actors are outside the original roster. Resolve dates/setup/config time fields only with room for that bounded relative body budget. A null closing reserves no future interval; near MAX, a late trusted close retains the existing capped-relative-deadline behavior and overdue item timeouts settle at MAX without fabricated readers/publication.
