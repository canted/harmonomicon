# Candidate 0.21 compatibility and migration

Base commit `c7b3fb9` contains candidate 0.20 and the package inspector cleanup. Candidate numbering follows the repository's incremental format directories; 0.21 is a local pre-1 candidate, not a release or 1.0 decision.

- **Format identity:** `harmonomicon.activity-package/0.21` negotiates exactly. A 0.20 host does not implicitly accept it. Import validates schema/semantic references; setup checks required operations, policies and capabilities before creating state.
- **Activity identity:** a package's `(id,version)` remains immutable with a canonical digest. Retained examples have new patch revisions because their envelopes changed. The four new witnesses use distinct IDs; three use initial `0.1.0` revisions and the predefined poll advances to `0.1.1` after review wording corrections. Running instances stay pinned; this is definition exchange, not running-state or blob transfer.
- **Operation identity:** all retained @1 contracts stay unchanged. In particular, collect choices remain one-submission literal choices, tally@1 still requires individual reveal, reveal@1 cannot reveal ballots, and the seeded assignment policy retains its exact algorithm. The new behavior uses vote@1, tally@2, select@1, present@1, reveal_ballots@1 and artifact_pool@2.
- **References:** new consumers validate preceding top-level types. A typed @2 pool feeds voting; existing assignment/response @1 operations continue to accept their original @1 source types. Voting consumes typed pools, not arbitrary forms, text-list fields, response collections or unrelated count results. Result input accepts typed selections, not predefined labels or free JSON paths.
- **Validation:** compare the complete 44-trace 0.20 engine corpus (34 retained, 4 image, 6 artifact) in separate historical processes against 0.21: exact outcomes, all actor views and full state. Retained HTTP, migration, media, recurrence, assignment, race, worker and exchange suites are rerun through both independently implemented hosts. Random tie sequences are intentionally not compared between unseeded hosts; exact injected choices and durable/property assertions validate their contract.
- **Historical files:** no previous format or validation directory is edited. No automatic persisted-state migration is supplied. Hosts must retain the old engine for existing instances or design their own explicit migration with further evidence.

## Migration accounting

Six of the twenty legacy 0.12 packages remain complete; fourteen remain incomplete. New voting and finite continuation witnesses do not increase that number. Caption-vote legacy packages still need their exact offers, response-derived candidates, eligibility and insufficient-source rules; private contribution contests are a useful simpler activity. prospective host app adoption support is a bounded core profile, not faithful historical/current Daily reproduction. [Migration checklist](MIGRATION.md) and [supported assessment](readiness-assessment.md) make these distinctions explicit.
