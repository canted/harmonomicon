# Migration checklist for the twenty 0.12 examples

This checklist measures migration of each earlier package's timing, supported setup choices, acceptance rules, missing-contribution behavior, and audience views. A similarly named activity with different rules is not a complete migration. Candidate 0.18 has twenty examples; they are not replacements for all twenty earlier packages.

**Current result:** four complete migrations; sixteen need additional operations or bindings; none is intentionally outside the proposed supported scope. All eighteen 0.17 examples carry forward with new package revisions and unchanged outcomes/views in the twenty-seven previous traces. Single-source linked responses add reusable pieces but do not complete any exact two-offer legacy migration. The three text daily-practice examples now have comparison evidence for their full selected legacy rules.

The [machine-readable checklist](migration.json) has one row for every earlier example. The checker verifies exact membership, no duplicates, concrete gaps for incomplete migrations, and existing evidence files for completed ones. An `expressible` row requires a runnable translated package and comparison evidence. `outside_scope` requires an explicit scope decision; no current row uses it.

## Completed: scheduled check-in

The [translated package](examples/scheduled-check-in.json) keeps the original package ID, uses a new revision, and reproduces the full selected text check-in: creation no later than opening, chosen opening/closing times, optional saved question, one private answer each, and ordered reveal only at closing. It retains the original 2–32 participant bounds.

[Six comparison scenarios](conformance/check-in-migration.json) include both original 0.12 fixtures, all-participant early completion, empty/partial windows, reads crossing deadlines, prompt overrides, retries and changed reuse, and the maximum safe closing time. The [reference comparison](migration_check.py) checks the unchanged collection model delegated by the 0.12 checker. The [HTTP trial](../../validation/0.18/README.md) also compares actual 0.12 and 0.18 implementations in both languages, including restart and worker-only close. A newly combined scheduled-check-in-to-pairs package transfers and runs in both apps.

This is behavior equivalence across format versions, not wire compatibility. 0.18 actions add an execution key; its views expose runbook records rather than the old `waiting/open/closed` object. The test adapter maps those shapes to compare phase, total count, each actor's own value, and the ordered reveal. It does not remove or transform contribution text, reorder entries, or grant additional access. Extra runbook metadata is allowed; malformed transport envelopes are governed by each version's own rules. Existing 0.12 instances are not upgraded or transferred as running instances.

## Completed: three text daily-practice packages

The translations preserve IDs, participant bounds, fixed prompts, first-opening setup, interval/window/count, one text entry per occurrence, between-window rejection, public complete/pending/missed status, accepted order, and all three visibility modes. [Nine comparison scenarios](conformance/recurrence-migration.json) include the three original fixtures, full day-sized histories with gaps/stale actions/replay, and maximum-safe final closing times. [Reference comparisons](recurrence_check.py) use the unchanged legacy model; [durable-host comparisons](../../validation/0.18/recurrence_trial.py) use actual retained 0.12 hosts in both languages. Restart preserves window identity and historical privacy.

This is behavior equivalence, not wire or running-instance compatibility. The adapter replaces legacy one-based `occurrence` with a zero-based invocation key and projects the same phase, ordered entries, own value and status facts. It does not trim values, reorder entries, or grant additional access. Current package settings do not add an instance prompt override to these fixed-prompt legacy examples.
