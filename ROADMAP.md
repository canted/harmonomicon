# Format roadmap

Harmonomicon develops activity package candidate 0.12. The earlier 0.x formats are historical candidates. This roadmap records their scope and the evidence that led to candidate 0.12. A future version number will be assigned only when its change and compatibility rules are defined.

## Three different versions

- The package's `format` value (for example, `harmonomicon.activity-package/0.12`) selects the shape and rules of the format.
- A package's `version` (for example, `1.0.0`) identifies a revision of that particular activity package. Changing its bytes requires a new package version; it does not change the format for every package.
- A behavior token (for example, `repeated_collection@1`) identifies exact runtime semantics. An app host must implement that token as specified or report it as unsupported. A future change to those semantics needs a new behavior token, not a silent change under `@1`.

An app host must explicitly support the format and every behavior and capability a package requires. Support for a newer format does not by itself imply support for an older one. The [0.12 versioning and conformance rules](format/0.12/README.md#versioning-and-conformance) define these distinctions.

## candidate 0.12 validation

The [25-card coverage audit](COVERAGE.md) classifies nine recognizable digital versions, eleven substantive but partial digital slices, and five boundary references. It does not count a prompt or timer as implementation of a physical, synchronous, or game-specific rule. The ten selected behavior contracts cover the recurring digital mechanisms identified in the [mechanism survey](research/mechanism-survey.md) and [digital stress cases](research/digital-activity-stress-cases.md); the audit names their missing source-specific rules.

The [0.12 specification](format/0.12/README.md) freezes the envelope, exact tokens, package identity and revision rules, exchange operations, unsupported handling, and full or partial app host conformance claims. Its [schema](format/0.12/package.schema.json), [examples](format/0.12/examples/), [41 conformance cases](format/0.12/conformance/README.md), and reference checker agree. The [trial with independent app hosts](validation/0.12/README.md) passes the same packages and traces through separate Python and Node.js SQLite services, with additional storage, access, worker, race, restart, and package-transfer probes. This validates the candidate subset for the stated local profile; it does not certify arbitrary app hosts or public deployments.

## Future advancement rule

A later release should start from a specific uncovered digital mechanism in the [coverage audit](COVERAGE.md), define its exact behavior or capability token and package compatibility, add schema/examples/conformance cases, and repeat independent app host validation. Likely separate extensions are local-calendar scheduling, open participation queues, post-to-view gates, alternating media, project media, and multi-criterion grading. Their order and version numbers are not fixed by 0.12. Existing `@1` token semantics and `(id, version)` package content must remain immutable; incompatible rules need new tokens or a new format identifier.
