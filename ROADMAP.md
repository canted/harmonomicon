# Format roadmap

Harmonomicon's current format is candidate 0.13. The earlier 0.x formats are historical candidates. Version 1.0 is reserved for a format in which a package can define an activity by composing reusable operations.

## Three different versions

- The package's `format` value (for example, `harmonomicon.activity-package/0.12`) selects the shape and rules of the format.
- A package's `version` (for example, `1.0.0`) identifies a revision of that particular activity package. Changing its bytes requires a new package version; it does not change the format for every package.
- A behavior token (for example, `repeated_collection@1`) identifies exact runtime semantics. An app host must implement that token as specified or report it as unsupported. A future change to those semantics needs a new behavior token, not a silent change under `@1`.

An app host must explicitly support the format and every behavior and capability a package requires. Support for a newer format does not by itself imply support for an older one. The [0.12 versioning and conformance rules](format/0.12/README.md#versioning-and-conformance) define these distinctions.

## Candidate 0.12 validation

The [25-card coverage audit](COVERAGE.md) classifies nine recognizable digital versions, eleven substantive but partial digital slices, and five boundary references. It does not count a prompt or timer as implementation of a physical, synchronous, or game-specific rule. The ten selected behavior contracts cover the recurring digital mechanisms identified in the [mechanism survey](research/mechanism-survey.md) and [digital stress cases](research/digital-activity-stress-cases.md); the audit names their missing source-specific rules.

The [0.12 candidate specification](format/0.12/README.md) defines the envelope, exact tokens, package identity and revision rules, exchange operations, unsupported handling, and full or partial app host conformance claims. Its [schema](format/0.12/package.schema.json), [examples](format/0.12/examples/), [41 conformance cases](format/0.12/conformance/README.md), and reference checker agree. The [trial with independent app hosts](validation/0.12/README.md) passes the same packages and traces through separate Python and Node.js SQLite services, with additional storage, access, worker, race, restart, and package-transfer probes. This validates the candidate subset for the stated local profile; it does not certify arbitrary app hosts or public deployments.

## Goal for 1.0

In 1.0, the package itself must define the app-mediated activity as a series of reusable, versioned operations. A package author must be able to arrange and configure operations such as opening a contribution window, assigning a turn or recipient, storing a private answer, collecting guesses, revealing selected information, and closing or recovering a step. The package must also define how steps advance, what data each step uses or produces, who may act or see it, and what happens at deadlines, retries, and missing contributions. These rules must be machine-readable package data, with exact semantics in the specification. Human-facing instructions remain part of the package but cannot substitute for app-executed rules.

The 1.0 gate requires all of the following:

1. A package schema and operation semantics that let authors make new activities by combining operations without writing a new complete behavior contract or changing app host code for each activity.
2. Deterministic event, timing, visibility, and recovery rules for those combinations, including unsupported-operation reporting and portable package identity.
3. Examples and conformance traces covering unlike activity families and held-out combinations. The [eight-pattern challenge](experiments/format-0.12-coverage-challenge/README.md) and [hidden-answer comparison](experiments/hidden-answer-composition/README.md) supply starting cases; 1.0 must address their composition failures, not just rename the ten existing contracts.
4. The same composed packages and traces running in two independent app hosts with separate implementations and durable state, including transfer, restart, concurrency, and privacy checks.

The [hidden-answer comparison](experiments/hidden-answer-composition/README.md) shows why this gate matters: a game-specific draft can run Two Truths and a Tall Tale, while a composed draft also runs a related List Game. Those drafts are experiments, not packages accepted by candidate 0.12. Additional tests across less similar activities must establish which operations are reusable and where a new primitive is needed. The [coverage audit](COVERAGE.md) identifies other digital mechanisms to test, including open queues, post-to-view gates, alternating media, reviewer allocation, and multi-criterion grading. Covering every group activity is not a 1.0 requirement.

Existing `@1` token semantics and `(id, version)` package content remain immutable. The eventual 1.0 identifier will have its own compatibility rules; support for candidate 0.12 does not imply support for 1.0 or vice versa.

## Path from 0.13 to 1.0

Candidate 0.13 completes the first runbook milestone: package authors can arrange reusable operations, pass typed references between steps, and run a new arrangement in independent app hosts. The [authoring guide](format/0.13/authoring.md) makes that authoring model concrete. The broader 1.0 coverage gate remains open.

| Milestone | Work | Required evidence |
|---|---|---|
| Next candidate: pools and assignments | Define multiple independent items per contributor, stable item identity, explicit recipient/group assignment, and views limited to the assigned audience. Specify each assignment policy's exact input, output, and version. | Gratefulness Grab Bag's two-slip pool and staged reader access; facilitator regrouping in Impromptu Networking; private pair/quartet views in 1-2-4-All. Include an unrelated held-out combination, same-item assignment races, and transfer in both app hosts. |
| Scoring and routed rounds | Add bounded numeric responses, card/round identity, deterministic aggregation and tied results; establish how assignments and scoring repeat across rounds. | The proposed 25/10 digital target: independent per-card ratings, hidden prior scores, exact totals and ranked reveal, with explicit routing and tie choices. Reuse the same operations in a different assessment activity. |
| Longer and media activities | Re-encode representative 0.12 flows as composed packages. Use the caption contest, a game jam with progress discussion beside a final deadline, and a repeated creative practice to test media, recurrence, and overlapping streams. Extend sequencing only where those witnesses require it. | Real media authorization, a progress stream that remains usable during other windows, missed-window recovery, restart, and equivalent results in both app hosts. Record which 0.12 behaviors are expressible and which require new operations. |
| Stabilization and 1.0 decision | Run the strict coverage challenge again, test additional activities held out during operation design, review authoring clarity, freeze operation/version rules, and publish the supported scope. | Broad coverage of selected simple digital mechanisms; the 1.0 requirements above all pass. Every remaining gap is named and bounded. Adding a new activity made from supported operations requires package data, not new app code. |

The next candidate's scope is assignment and audience semantics, rather than a new complete activity contract. It must preserve the demonstrated composition property: operations can be ordered by the package, and app code dispatches on operations and versioned policies. There is no fixed number of candidate releases before 1.0; a failed milestone leads to a revised candidate and repeated evidence.
