# Format roadmap

Harmonomicon has candidate format versions, not a published standard. This roadmap records what each candidate defines, what has been tested, and what evidence is needed to advance it. Version numbers beyond 0.8 are provisional; a later candidate gets its number when its scope is settled.

## Three different versions

- The package's `format` value (for example, `harmonomicon.activity-package/0.2`) selects the shape and rules of the format candidate.
- A package's `version` (for example, `0.2.0`) identifies a revision of that particular activity package. Changing its bytes requires a new package version; it does not change the format for every package.
- A behavior token (for example, `repeated_collection@1`) identifies exact runtime semantics. A host must implement that token as specified or report it as unsupported. A future change to those semantics needs a new behavior token, not a silent change under `@1`.

A host must explicitly support the format and every behavior and capability a package requires. Support for a newer format does not by itself imply support for an older one. These distinctions follow the [package identity, contract, and capability rules](format/0.2/README.md).

## Project-cycle boundary

The [game-jam and shared-practice survey](research/creative-jams-and-shared-practice.md) and [ongoing-activity experiment](experiments/ongoing-activities/findings.md) identified a work-period gap in the first four contracts. Candidate 0.5 closes a defined part of it: fixed teams can make private or group progress posts, comment, submit one final entry, and review other teams later. Its [contract](format/0.5/README.md), [cases](format/0.5/conformance/README.md), and [two-host result](validation/0.5/README.md) establish the text version under local conditions. Team formation, changing membership, media files, ratings, and a winner remain separate questions.

The [mechanism survey](research/mechanism-survey.md) and [digital stress cases](research/digital-activity-stress-cases.md) still leave other digital patterns to assess: facilitator-controlled phase and group changes, opt-in or permissioned contribution, stalled-turn recovery, image media, and selection or voting. A coverage audit of the source-backed activity cards will decide the next slice and the 1.0 behavior set. Publication depends on the gate below, not a particular 0.x number.

## Ongoing-space boundary

The [coverage audit](COVERAGE.md) identified an ongoing journal or creative space as a gap in fixed repeated windows. Candidate 0.6 defines retained private or shared entries, comments, and an optional prompt series with explicit completion-status visibility. Its [contract](format/0.6/README.md), [cases](format/0.6/conformance/README.md), and [two-host result](validation/0.6/README.md) establish this text slice under local conditions. Local-calendar days, external media, editing/deletion, and verification of offline work remain outside it.

The [coverage audit](COVERAGE.md#coverage-decisions) still identifies facilitated phases, turn recovery, and media/selection as broad untested families. The next candidate will be chosen from those gaps, and publication will depend on the gates below rather than a particular 0.x number.

## Guided-rounds boundary

The [mechanism survey](research/mechanism-survey.md) identified timed phases and changing groups as a gap in the earlier contracts. Candidate 0.7 defines a fixed sequence of timed prompts with validated group partitions and three audience choices. Its [contract](format/0.7/README.md), [cases](format/0.7/conformance/README.md), and [two-host trial](validation/0.7/README.md) establish a digital text slice under local conditions. Facilitator-controlled permission, early manual advancement, real-world performance, and low-latency live audio remain outside it.

The [coverage audit](COVERAGE.md#coverage-decisions) still identifies turn recovery and media/selection as broad untested families. The next candidate will be chosen from those gaps. Publication depends on the gates below rather than a particular 0.x number.

## Recoverable-handoff boundary

The [digital activity stress cases](research/digital-activity-stress-cases.md) and [offer-flow experiment](experiments/offer-flows/findings.md) isolate a stalled asynchronous chain: the next person may never answer, while two simultaneous offers need one authoritative winner. Candidate 0.8 defines a bounded `competitive_handoff@1` text contract with organizer-supplied offer pairs, a trusted deadline for each attempt, optional participant decline, automatic fallback to a second pair, one atomic accepted contribution per step, and a terminal stalled state when all attempts fail. Only the currently offered actors see the immediate input; a completed chain is revealed to the group. Assignment fairness and the actual text or image creative task remain outside the host's judgment.

The 0.8 gate includes a schema and package example, conformance traces for competing submissions, exact deadline races, decline, timeout/fallback, stall, privacy, replay, and invalid route setup, and two independent hosts passing the same cases through durable transactions, workers, and authenticated views. The 0.7 behavior set and 0.4 exchange rules remain in force. The [coverage audit](COVERAGE.md#coverage-decisions) then leaves media/selection and permissioned facilitation as the broad remaining gaps before choosing a 1.0 set.

## Next candidate: portable image references

The [coverage audit](COVERAGE.md#coverage-decisions) shows that image contributions recur across caption games, photo prompts, collaborative drawing, and project showcases. The [image-caption example](format/0.8/examples/image-caption-circle.json) already requires `image_ref@1`, but the text-only hosts correctly report it as unsupported. Candidate 0.9 will define the exact meaning of an image reference and the host storage and access duties that make it real, while retaining the eight 0.8 behavior contracts. It will run the image-caption package through both hosts, including image upload, source offers, caption submission, and reveal.

The 0.9 gate is a normative media-reference contract, schema and example alignment, conformance cases for valid/invalid images, duplicate bytes, private source access, offered-source access, deadline and retry behavior, plus two independent hosts storing actual bytes and enforcing authenticated media reads after restart. Media references will identify content within an instance; package exchange will still transfer package definitions rather than private participant uploads. Voting, scoring, file types beyond the chosen image subset, malware scanning, public CDN delivery, and moving a running instance are outside this slice. The [roadmap publication gate](#toward-10) remains independent of the candidate number.

## Advancement rule for a candidate

A candidate is **defined** when its normative document, machine-readable schema, example packages, and conformance cases agree on inputs, outcomes, boundaries, and participant views. It is **reference checked** when those cases pass a reference model and invalid cross-field combinations are rejected. It is **two-host validated** when independent implementations load the same packages and produce the specified outcomes through real storage, scheduling, and access boundaries. Localhost services are sufficient for that gate; public web deployment is a separate operational test.

Each new behavior must state its exact token, required host capabilities, trusted inputs, event and retry semantics, deadline or ordering rules, views for each audience, and unsupported response. A candidate must record what it does not cover. When evidence exposes a mismatch, revise the unpublished candidate with new cases; after a version is published, incompatible semantics require a new version or token.

## Toward 1.0

A 1.0 release is a publication gate, not a promise to model every group activity. Before it, the selected behavior set needs a stable package format, a way for hosts to report supported format/behavior/capability versions, conformance cases for every required behavior, and at least two independent hosts passing those cases at their storage and access boundaries. The publication also needs explicit rules for package-version changes, backward compatibility, and what a conformance claim means. Running-instance migration, general code execution in packages, every media type, and public hosting are separate capabilities unless deliberately included and tested.

The [research synthesis](research/contract-synthesis.md) explains why the project is advancing with precise behavior contracts and host evidence rather than treating one experimental JSON shape as a universal activity language.
