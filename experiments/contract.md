# Contract 0.1: deliberately small transition vocabulary

This is a **test language**, not a normative plugin protocol. Definitions are UTF-8 JSON objects. IDs, actor names, capabilities, and event names are locally scoped strings. Both interpreters implement the rules below using standard libraries.

## Definition

```json
{
  "format": "activity-experiment/0.1",
  "id": "example",
  "requires": ["events"],
  "actors": {"host": "host", "alice": "participant"},
  "content": {"title": "Example", "sourceCard": "../../research/activities/example.md", "setup": "...", "steps": ["..."], "completion": "...", "source": "https://..."},
  "initial": {"phase": "ready"},
  "transitions": [],
  "views": []
}
```

`requires` is a set of named host capabilities. `actors` maps known IDs to exactly one role; this experiment does not model role changes or authentication. `content` carries concise, paraphrased human instructions and evidence attribution. Its text is portable data, but the interpreters do not render it or check whether participants understood it. `initial` is JSON state. A trace supplies a set of host capabilities. Missing required capabilities return `unsupported` with the sorted missing names, without processing events.

## Events and transitions

Every event has `{ "type": string, "actor": string, "at": integer, "payload": object }`. `at` is supplied by the host and is not independently trusted or generated by the interpreter. A transition has `on`, `by` (allowed roles), optional `if` (all conditions must hold), and `do` (ordered actions). If exactly one transition matches, apply its actions atomically; otherwise reject the event and keep the prior state. Unknown actors reject. The event log in each fixture records the outcome, but rejected events are not appended to activity state.

## Values and conditions

An object of the form `{ "ref": "state.path" }` or `{ "ref": "event.payload.path" }` reads that value. `event.actor`, `event.at`, and `event.type` are also readable. Other JSON values, including objects and arrays, are literals. Dot paths name object keys only; there is no array indexing, computed property access, arithmetic expression, or arbitrary code. A missing reference fails a condition or action.

Each condition has `op`, `left`, and usually `right`. Supported operations are `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `has_key`, `lacks_key`, and `length_eq` / `length_lt` / `length_gte`. Ordered comparisons require numbers. `has_key` and `lacks_key` require an object and string key; length operations require an array. Equalities compare JSON values structurally. A condition with a missing reference is false. Conditions in `if` are joined by AND; separate transitions for the same event provide distinct branches.

## Actions

All action paths target existing state object paths, except `put` adds or replaces a key inside an existing object.

| Operation | Fields | Effect |
|---|---|---|
| `set` | `path`, `value` | Replace the value at the state path. |
| `add` | `path`, `value` | Add numeric value to numeric state field. |
| `append` | `path`, `value` | Append value to array state field. |
| `put` | `path`, `key`, `value` | Set a string-keyed value in object state field. |
| `partition` | `path`, `value`, `sizes` | Replace a grouping object after checking every listed actor appears exactly once and every group size is allowed. `value` is an object of group IDs to arrays of actor IDs; `sizes` is a list of allowed lengths. |

`partition` checks members against all actors whose role is `participant`. It does not choose groups; an authorized host supplies them. This is a deliberately narrow way to test externally assigned groups without pretending the package contains a pairing algorithm.

## Views

Each `views` entry has `field` (a top-level state key), `by` (roles), and optional `if` conditions. For a view request, the interpreter creates an event-like context `{ "actor": requestedActor }`. A field is copied into the view if **exactly one or more** rules for it match; multiple matching view rules are an OR, unlike transition selection. Unknown actors get `unknown_actor`. Nested redaction is not supported, so data with different audiences must be held in different top-level fields. This limitation is intentional and is assessed in [findings.md](findings.md).

## Fixture output

The output object has `status` (`ok` or `unsupported`), `state` and `outcomes` for supported cases, plus `views` for requested actors. Each outcome is `accepted` or `rejected`; the interpreters do not expose internal error text as conformance output. `unsupported` output has only `status` and `missing`. Fixtures compare JSON structure without relying on object-key order.
